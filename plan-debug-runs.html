Dossiers de run « debug » par requête

Un dossier horodaté par appel assess(), avec un fichier .md lisible qui déballe en clair les appels LLM et la recherche de contrat — pour comprendre et débugger une requête à la main.

Date : 2026-07-22 Portée : traçabilité debug locale (dev-only) Approche : TDD, offline

Objectif & portée

Aujourd'hui, la seule trace d'une requête est logs/policybot.jsonl (via policybot/tracing.py) : structuré, une ligne JSON par étape, mais le texte libre y est systématiquement masqué (longueur + hash SHA-256 seulement). Impossible de relire un prompt ou une réponse LLM à l'œil.

On ajoute un canal parallèle, dev-only : à chaque appel Interview.assess(), si le flag est activé, on crée un dossier de run horodaté contenant un fichier .md qui expose en clair :

  • Volet 1 Appels LLM détaillés — pour chaque appel : call site (run_name/tags/task), prompt système + utilisateur, réponse brute, tokens, coût.
  • Volet 2 Recherche de contrat — l'objet ContractEvidence : documents trouvés par fait (URL, titre, source, extrait), faits retenus avec citation verbatim, faits en échec.

Un court entête d'identification (interview_id, outil, horodatage, coût total) coiffe le fichier pour le rendre autosuffisant — mais pas de section verdict/synthèse détaillée (hors périmètre choisi).

Décisions verrouillées (issues des questions préalables) :
  • Texte libre en clair, dans un dossier debug local gitignoré.
  • Contenu = appels LLM + recherche contrat uniquement (+ entête d'ID).
  • Structure : logs/runs/AAAA-MM-JJ_HH-MM-SS_<id>/ — un dossier par requête.
  • Activable par flag env, off par défaut, en plus du JSONL existant (qui ne change pas).
  • Granularité : un fichier par appel assess() (donc plusieurs fichiers possibles pour un même parcours web wizard — assumé).

⚠️ La contrainte de confidentialité — à traiter en premier

Le CLAUDE.md pose une règle non négociable : « never log free text in the clear ». Ce plan crée délibérément une exception locale et opt-in. On l'encadre pour qu'elle ne devienne jamais une fuite :

Garde-fouMise en œuvre
Jamais versionnélogs/runs/ ajouté au .gitignore (vérifier que logs/ l'est déjà ; sinon cibler logs/runs/ explicitement).
Off par défautRien n'est écrit sans POLICYBOT_DEBUG_RUNS=1. Le comportement de prod est inchangé.
Le JSONL reste masquéOn ne touche pas à tracing.py / mask_text(). Le canal masqué et le canal clair coexistent.
Avertissement dans le fichierEntête du .md : bandeau « contient du texte non masqué — ne pas partager / ne pas committer ».

Règle d'or : ce canal est un outil de développement local. Il ne doit jamais être activé dans un déploiement partagé, ni son dossier committé.

Architecture — comment ça s'accroche au code existant

On réutilise le patron déjà présent dans tracing.py : un contextvar qui porte l'état du run courant à travers toute la pile d'appels, ouvert/fermé par un context manager autour de assess() — exactement comme collect_llm_usage() le fait déjà pour les compteurs de tokens.

Nouveau module : policybot/debug_run.py

  • Un contextvar _current_debug_run: ContextVar[DebugRun | None] (défaut None = désactivé).
  • DebugRun (dataclass) accumule llm_calls: list[LLMCallRecord] et contract_searches: list[ContractSearchRecord], plus les métadonnées d'entête.
  • LLMCallRecord : method (json/structured/text), run_name, tags, task, system, user, response (str), tokens, cost, duration_ms, status.
  • ContractSearchRecord : tool_name, source, documents_by_fact, facts (citations), failed_facts.
  • @contextmanager debug_run(interview_id, tool_name) : si le flag est off → yield sans rien faire ; si on → crée le DebugRun, le pose dans le contextvar, et à la sortie écrit le dossier + le .md.
  • Helpers record_llm_call(...) / record_contract_search(...) : no-op si aucun run actif (comme record_llm_call_started() aujourd'hui).

Capture des appels LLM — DebugRecordingProvider (wrapper)

Plutôt que de modifier chaque provider (OpenRouterProvider, FakeLLMProvider), on introduit un décorateur LLMProvider qui enveloppe le provider injecté. Il implémente complete_json / complete_structured / draft_text, délègue au provider réel, et enregistre system/user/réponse dans le run courant. Non-invasif, testable isolément.

Sérialisation des réponses : complete_json → json.dumps du dict ; complete_structured → model_dump() du pydantic ; draft_text → la chaîne telle quelle.

Capture de la recherche de contrat

Dans Interview._resolve_arp() (orchestrator.py, bloc resolve_arp_fetch), l'objet ContractEvidence (URLs, extraits, facts avec citations, failed_facts) est déjà en main juste avant l'extraction. On appelle record_contract_search(tool_name, source, evidence) à cet endroit. note Le code actuel passe par contract/exa.py + fact_search.py + evidence.py (Exa), pas Tavily/families.py comme le dit le CLAUDE.md — se fier au code.

Flux de bout en bout

assess(request, tool_name, usages) │ ├─ with collect_llm_usage(id): # existant, inchangé │ └─ with debug_run(id, tool_name): # NOUVEAU — no-op si flag off │ │ │ ├─ classify_data(...) ──► DebugRecordingProvider capte prompt+réponse ─┐ │ ├─ _resolve_arp(...) │ │ │ └─ record_contract_search(evidence) ── capte URLs + citations ├─► DebugRun │ ├─ extract_contract_facts(...) ──► capte prompt+réponse ────────────────┤ (contextvar) │ ├─ evaluate_usage / synthesize (déterministe, non capté) │ │ │ │ │ └─ (sortie du context manager) ─► écrit logs/runs/<ts>_<id>/run.md ◄─────┘ │ └─ return InterviewState

Chaque appel assess() ouvre son propre debug_run ; les contextvars étant isolés par contexte d'exécution, deux requêtes concurrentes (API async, wizard) écrivent dans deux dossiers distincts sans collision.

Structure produite sur disque

logs/ ├─ policybot.jsonl # existant (masqué) — inchangé └─ runs/ # NOUVEAU — gitignoré └─ 2026-07-22_14-03-58_a1b2c3d4/ └─ run.md # un fichier par appel assess()

Nom du dossier : <date>_<heure>_<8 premiers car. de l'interview_id>. Le dossier (plutôt qu'un simple fichier) laisse la place à de futurs artefacts — HTML de termes récupérés, dumps de prompts bruts — sans casser le nommage.

Découpage en phases (TDD)

Phase 0 — Garde-fous privacy

  1. Gitignore : confirmer/ajouter logs/runs/ dans .gitignore.
  2. Flag : lire POLICYBOT_DEBUG_RUNS ; centraliser dans policybot/config.py à côté des autres réglages env.

Phase 1 — Module debug_run.py + context manager

  1. Test d'abord : flag off ⇒ aucun dossier créé, record_* sont des no-op.
  2. Test : flag on ⇒ à la sortie de debug_run(), un dossier logs/runs/<ts>_<id>/run.md existe (rediriger la racine via une variable, comme POLICYBOT_LOG_PATH le fait pour les tests).
  3. Impl : contextvar, dataclasses DebugRun/LLMCallRecord/ContractSearchRecord, helpers, création de dossier.

Phase 2 — DebugRecordingProvider

  1. Test : wrapper autour d'un FakeLLMProvider ⇒ le run courant contient 1 LLMCallRecord avec system/user/réponse exacts pour chaque méthode.
  2. Test : délégation transparente — la valeur de retour est identique au provider sous-jacent.
  3. Impl : les 3 méthodes + sérialisation par type de réponse.

Phase 3 — Capture recherche contrat

  1. Test : _resolve_arp() avec un exa_search injecté renvoyant une ContractEvidence ⇒ le run contient 1 ContractSearchRecord avec faits + citations + failed_facts.
  2. Impl : appel record_contract_search(...) dans le bloc resolve_arp_fetch.

Phase 4 — Rendu du run.md

  1. Test : un DebugRun peuplé ⇒ le markdown produit contient l'entête d'ID, chaque appel LLM, chaque fait de contrat, le bandeau d'avertissement.
  2. Impl : fonction render_run_md(run) -> str pure (facile à tester), puis écriture disque dans le context manager.
  3. Robustesse : l'écriture ne doit jamais faire échouer assess() — envelopper dans un try/except qui, au pire, log un warning (comme la dégradation Exa ne casse pas l'entrevue).

Phase 5 — Câblage

  1. Orchestrator : ouvrir debug_run(state.interview_id, tool_name) à l'intérieur de collect_llm_usage dans assess().
  2. Provider : dans api/deps.py (default_interview()), envelopper le provider choisi dans DebugRecordingProvider quand le flag est on.
  3. Test d'intégration : un assess() complet avec FakeLLMProvider + exa_search injecté ⇒ un run.md lisible de bout en bout.

Phase 6 — Doc

  1. CLAUDE.md : documenter l'exception privacy + le flag, et corriger la mention Tavily→Exa au passage si pertinent.
  2. .env.example : ajouter POLICYBOT_DEBUG_RUNS= commenté.

Risques & mitigations

Fuite de texte libre. Le fichier contient du contenu non masqué. → Gitignore logs/runs/, flag off par défaut, bandeau d'avertissement dans chaque fichier, doc explicite. Ne jamais activer en déploiement partagé.
Plusieurs fichiers par parcours web. Le wizard appelle assess() à chaque étape (interview_id différent) → N dossiers pour un même parcours. Assumé (choix « un fichier par appel assess() »). L'entête d'ID permet de les relier si besoin plus tard.
Écriture qui casse l'entrevue. Un souci d'I/O ne doit jamais faire échouer assess(). → Écriture enveloppée dans try/except, dégradation silencieuse + warning, jamais d'exception propagée.
Étapes déterministes non captées. Matrice, règles grille, synthèse ne passent pas par le LLM et sortent donc du périmètre choisi. Elles restent visibles dans le JSONL masqué existant si besoin.

Critères de « fait »

  • Avec POLICYBOT_DEBUG_RUNS=1, un appel assess() produit exactement un logs/runs/<ts>_<id>/run.md lisible, contenant tous les appels LLM (prompt + réponse en clair) et la recherche de contrat (URLs + citations).
  • Sans le flag : aucun dossier créé, comportement et JSONL strictement inchangés.
  • logs/runs/ est gitignoré ; chaque fichier porte le bandeau d'avertissement.
  • pytest -v passe intégralement, offline et déterministe (nouveaux tests inclus).
  • Une erreur d'écriture debug ne fait jamais échouer une requête.
