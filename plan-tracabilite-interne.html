Couche de traçabilité interne — PolicyBot

Journaliser chaque étape du pipeline d'évaluation (interview → classification → ARP → LLM → grille) pour comprendre rapidement ce que l'application fait, sans jamais écrire de renseignements personnels en clair dans les fichiers de log.

Date : 2026-07-06 Portée : débogage local, solo dev Échéancier : cette semaine Stockage : fichiers locaux (JSON lines)

Contexte & décisions issues des questions

GranularitéChaque étape du pipeline, reliée par un interview_id commun
Données sensiblesLe texte libre (descriptions d'usage, contenu LLM) ne doit jamais apparaître en clair — seulement longueur + hash + résultats de classification
Pourquoi ce dernier point compte particulièrement ici : PolicyBot classifie explicitement des données comme rens_personnels / « Protégé B/C ». Une couche de logs qui recopierait le texte brut créerait elle-même une nouvelle fuite de renseignements personnels dans un fichier non protégé. Le design ci-dessous traite ça comme une contrainte dure, pas une option.

Vue d'ensemble de l'architecture actuelle (état des lieux)

Aucune journalisation n'existe actuellement dans policybot/ (aucun import logging trouvé). Le point d'entrée réel est :

  • policybot/api/app.py → run_graph() (LangGraph, un seul nœud) → Interview.assess()
  • policybot/interview/orchestrator.py — Interview.assess() : classification des données, résolution ARP (cache ou fetch + LLM), évaluation de la grille
  • policybot/classify/data_classifier.py — classify_data() appelle llm.complete_json()
  • policybot/llm/openrouter.py / policybot/llm/fake.py — un seul point de passage : _chat()
  • policybot/grille/engine.py — evaluate_usage() / synthesize(), purement déterministe (pas d'appel LLM)

Ce pipeline est linéaire et déjà bien découpé en fonctions pures — c'est un bon terrain pour instrumenter sans le réécrire.

Phase 1 — Module de tracing central

Fondation
  1. Créer policybot/tracing.py avec un logger dédié (logging.getLogger("policybot.trace")), un Formatter qui sérialise chaque enregistrement en une ligne JSON, et un RotatingFileHandler pointant vers logs/policybot.jsonl (5 Mo × 5 fichiers de backup, pour éviter une croissance illimitée).
  2. Exposer un context manager trace_step(interview_id, step, **fields) qui mesure la durée, journalise un événement ok ou error à la sortie, et ré-émet toute exception après l'avoir journalisée (jamais d'exception avalée).
  3. Exposer mask_text(text: str) -> dict : retourne {"len": ..., "sha256": ...[:12]}. C'est le seul moyen autorisé de faire apparaître un texte libre dans les logs.
  4. Rendre le chemin du fichier de log configurable via une variable d'environnement POLICYBOT_LOG_PATH (défaut : logs/policybot.jsonl), pour ne pas polluer le repo ni les tests.

Esquisse de l'API

# policybot/tracing.py import time, json, logging, hashlib from contextlib import contextmanager from logging.handlers import RotatingFileHandler _logger = logging.getLogger("policybot.trace") _logger.setLevel(logging.INFO) _logger.propagate = False def mask_text(text: str) -> dict: return {"len": len(text), "sha256": hashlib.sha256(text.encode()).hexdigest()[:12]} @contextmanager def trace_step(interview_id: str, step: str, **fields): start = time.monotonic() try: yield except Exception as exc: _emit(interview_id, step, "error", time.monotonic() - start, error=type(exc).__name__, message=str(exc), **fields) raise else: _emit(interview_id, step, "ok", time.monotonic() - start, **fields) def _emit(interview_id, step, status, duration, **fields): _logger.info(json.dumps({ "ts": time.time(), "interview_id": interview_id, "step": step, "status": status, "duration_ms": round(duration * 1000, 1), **fields, }))
Pas de nouvelle dépendance : tout repose sur logging et hashlib de la stdlib, conforme à l'objectif « rapide, cette semaine ».

Phase 2 — Instrumenter l'orchestrateur

Cœur du pipeline
  1. Dans Interview.assess() (policybot/interview/orchestrator.py:51) : englober tout le corps dans trace_step(state.interview_id, "assess", tool=tool_name), juste après la création de state.interview_id.
  2. Autour de chaque appel classify_data(...) (ligne 71-73) : trace_step(interview_id, "classify_data", usage_index=i, **mask_text(item["data_description"])), puis journaliser le résultat (data_classification, rens_personnels, confidence, needs_officer_confirmation) comme champs additionnels — jamais le texte source.
  3. Dans _resolve_arp() (ligne 40) : journaliser cache=hit ou cache=miss, et si fetch_terms/extract_contract_facts sont appelés, envelopper cette branche dans son propre trace_step.
  4. Autour de chaque evaluate_usage(...) (ligne 88) : journaliser usage_index, matrix_result, risk_level, verdict.
  5. Après synthesize() (ligne 90) : journaliser le résultat global (risk_level, recommendation, efvpr_required).
  6. UnknownToolError (déjà levée avant la création de tracing utile) : journaliser un événement d'erreur minimal avant de laisser l'exception remonter — tool_name connu, interview_id pas encore généré à ce stade, donc utiliser un id temporaire ou déplacer la génération de l'id plus tôt dans assess().
Petit ajustement nécessaire : state.interview_id est généré à la ligne 54, mais lookup_tool / classify_tool_type (lignes 55-56) peuvent lever UnknownToolError avant. Il faudra générer l'interview_id en tout premier, avant tout risque d'exception, pour que même les échecs précoces soient traçables.

Phase 3 — Instrumenter la couche LLM

Appels externes
  1. Dans policybot/llm/openrouter.py, envelopper _chat() (seul point de passage pour complete_json et draft_text) : journaliser model, json_mode, durée, code HTTP, et en cas d'erreur (httpx.HTTPStatusError) le statut et le message — jamais le contenu de system/user/la réponse, seulement leurs longueurs via mask_text.
  2. Faire de même dans policybot/llm/fake.py pour que les traces de test ressemblent à celles de prod (utile pour les tests de la Phase 6 qui tournent sans clé API).
  3. Comme les deux providers implémentent LLMProvider, envisager un seul point d'instrumentation générique : soit un décorateur appliqué aux deux classes, soit un petit wrapper TracedLLMProvider qui enveloppe n'importe quel LLMProvider et que deps.py pourrait injecter — évite de dupliquer la logique de tracing dans chaque provider.

Phase 4 — Instrumenter l'API

Frontière externe
  1. Dans policybot/api/app.py, journaliser la réception de POST /assess (tool_name, pas le payload complet) et la réponse (succès ou 422 unknown_tool).
  2. Comme le graphe LangGraph n'a qu'un seul nœud aujourd'hui, il n'a pas besoin de tracing propre — Interview.assess() couvre déjà tout le travail utile. À revisiter si le graphe devient multi-nœuds.

Phase 5 — Tests

Garde-fou
  1. tests/test_tracing.py : lancer Interview.assess() avec FakeLLMProvider et un handler de log en mémoire ; vérifier qu'au moins un événement par étape attendue (assess, classify_data, resolve_arp, llm_call, evaluate_usage) est émis, et que tous partagent le même interview_id.
  2. Test anti-fuite (le plus important) : passer une data_description contenant une chaîne sentinelle reconnaissable (ex. un faux NAS/email) et affirmer que cette chaîne n'apparaît nulle part dans les lignes de log capturées — seulement sa longueur et son hash.
  3. Un test d'erreur : déclencher UnknownToolError et vérifier qu'un événement status=error est bien journalisé avant la propagation de l'exception.

Phase 6 — Documentation

Finition
  1. Ajouter une section « Traçabilité / logs » au README.md : emplacement du fichier (logs/policybot.jsonl), comment le lire (tail -f + jq), comment changer le chemin via POLICYBOT_LOG_PATH.
  2. Ajouter logs/ au .gitignore pour ne jamais committer de fichiers de log locaux.

Risques & mitigations

Fuite de renseignements personnels dans les logs. Mitigation : mask_text() comme seul chemin autorisé pour tout texte libre ; test anti-fuite en Phase 5 non négociable avant de considérer la fonctionnalité terminée.
Croissance illimitée du fichier de log. Mitigation : RotatingFileHandler avec taille max + nombre de backups dès la Phase 1.
Sur-ingénierie / dérive de portée. Le besoin exprimé est un outil de débogage solo, pas un système d'audit. Mitigation : rester sur fichiers JSON lines + stdlib, ne pas construire de dashboard ni intégrer un service externe (LangSmith etc.) dans cette itération — à revisiter seulement si le besoin de conformité devient explicite.

Critères de succès (« done »)

  • Chaque appel à Interview.assess() produit une trace JSON lines dans logs/policybot.jsonl, avec un interview_id commun reliant toutes les sous-étapes (classification, ARP, appel LLM, évaluation, synthèse).
  • Aucun texte libre brut (description d'usage, contenu de contrat, prompt/réponse LLM) n'apparaît jamais dans le fichier de log — uniquement longueur/hash/champs structurés.
  • Les erreurs (UnknownToolError, échecs HTTP du LLM) sont journalisées avec type + message + interview_id avant de remonter.
  • tests/test_tracing.py passe, y compris le test anti-fuite.
  • Le README documente l'emplacement des logs et comment les consulter.

Questions ouvertes

  • Si un besoin de conformité/audit émerge plus tard, faudra-t-il migrer ces traces vers SQLite ou un service dédié — à garder en tête comme extension possible, pas à construire maintenant.
