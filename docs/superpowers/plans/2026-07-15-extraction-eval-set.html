Jeu d'évaluation de l'extraction ARP (golden set)

Mesurer la vraie qualité d'extraction des faits contractuels (ContractFacts) contre une vérité terrain rédigée à la main, sur 3 outils réels — hors suite pytest déterministe.

Date : 2026-07-15 Branche : tavily-fetcher-evidence Exécutant : toi + Claude Code, en solo Échéance : aucune

Pourquoi ce plan existe

policybot/contract/arp.py extrait 16 faits contractuels via un LLM, avec citation verbatim obligatoire et vérification d'ancrage (_quote_is_anchored, déjà en place) contre le texte source. La suite pytest -v reste volontairement 100 % offline (FakeLLMProvider) : elle prouve que la plomberie tient (schéma, dégradation, ancrage), mais ne peut jamais dire si le LLM a extrait la bonne information sur un vrai contrat.

Ce plan ajoute un harnais séparé qui appelle le vrai LLM sur des preuves de contrats réelles et figées, comparées à une vérité terrain validée à la main — pour suivre la fiabilité d'extraction dans le temps (ex. après un changement de prompt ou de modèle), sans jamais toucher au caractère déterministe de pytest -v.

Phase 1 — Loader des cas golden (TDD)

  1. Étape 1.1 : Écrire un test qui pointe vers un dossier golden temporaire (tmp_path) contenant un evidence.txt factice (en-tête # source: ... \n# fetched_at: YYYY-MM-DD puis le texte) et un expected.yaml factice à 2-3 champs. Le test attend qu'une fonction load_golden_case(dir) -> GoldenCase retourne une ContractEvidence (via ContractEvidence.from_single) et un dict[str, str] de valeurs attendues.
  2. Étape 1.2 : Implémenter GoldenCase (dataclass : tool_slug, evidence: ContractEvidence, expected: dict[str, str]) et load_golden_case dans extraction_eval.py. Parser l'en-tête de evidence.txt pour source_url/fetched_at, le reste comme text. Utiliser yaml.safe_load pour expected.yaml (déjà une dépendance du projet).
  3. Étape 1.3 : Ajouter un test qui valide que expected.yaml ne référence que des clés existantes dans ALL_FACT_FIELDS (policybot/contract/families.py) — échoue fort si une fixture golden réelle contient une faute de frappe de champ.
  4. Étape 1.4 : Ajouter discover_golden_cases() -> list[GoldenCase] qui itère tests/contract/fixtures/golden/*/ — testé avec les vrais dossiers une fois créés en Phase 3, mais la fonction elle-même est testable dès maintenant avec un répertoire temporaire.
  5. Fin de phase : pytest tests/contract/test_extraction_eval.py -v passe, aucune fixture réelle requise.

Phase 2 — Notation et rapport (TDD)

  1. Étape 2.1 : Écrire les tests de score_field(expected: str, extracted: FactEvidence) -> Verdict pour les 3 verdicts : MATCH (valeurs égales, y compris unknown == unknown), WRONG_VALUE (extrait non-unknown ≠ attendu), WRONG_ABSTAIN (extrait unknown, attendu ≠ unknown).
  2. Étape 2.2 : Implémenter Verdict (enum ou Literal) et score_field.
  3. Étape 2.3 : Écrire les tests de score_case(case: GoldenCase, facts: ContractFacts) -> list[FieldResult] (FieldResult : field, expected, got, verdict) — avec un ContractFacts construit à la main, sans LLM.
  4. Étape 2.4 : Implémenter score_case.
  5. Étape 2.5 : Écrire les tests de format_report(results: dict[str, list[FieldResult]]) -> str : vérifie que le tableau par outil/champ apparaît, que le résumé agrégé affiche le taux de WRONG_VALUE en évidence, et que has_wrong_value(results) -> bool retourne juste selon le contenu.
  6. Étape 2.6 : Implémenter format_report et has_wrong_value.
  7. Fin de phase : tests de notation/rapport 100 % verts, toujours sans réseau ni LLM.

Phase 3 — Collecte de la vérité terrain (3 outils réels)

  1. Étape 3.1 : Claude récupère (WebFetch) les vraies pages : CGU OpenAI (openai.com/policies/terms-of-use), conditions consommateur Anthropic (anthropic.com/legal/consumer-terms), et les termes Microsoft Copilot Entreprise pertinents. Extrait les passages utiles (pas la page entière si elle est énorme — un extrait raisonnable et représentatif suffit).
  2. Étape 3.2 : Claude rédige un premier jet de expected.yaml par outil (16 champs, valeur + brève justification en commentaire YAML) à partir de ces pages, et écrit evidence.txt (en-tête source/date + texte figé).
  3. Étape 3.3 : CHECKPOINT L'utilisateur relit les 3 expected.yaml et corrige toute valeur douteuse avant qu'on les considère figés. Aucune étape suivante ne dépend de la perfection du premier jet, mais ce fichier fait foi une fois validé.
  4. Étape 3.4 : Ajouter un test simple par outil (test_golden_chatgpt_expected_is_well_formed, etc., ou un test paramétré sur discover_golden_cases()) qui vérifie que chaque expected.yaml couvre bien les 16 champs et ne référence que des valeurs autorisées (allowed_values de FactField).
  5. Fin de phase : 3 dossiers golden réels, validés par l'utilisateur, pytest -v toujours vert et toujours offline.
Les CGU réelles changent avec le temps. evidence.txt est un instantané figé volontairement — s'il dérive trop de la page actuelle, c'est un signal pour rafraîchir la fixture, pas un bug du harnais.

Phase 4 — CLI d'évaluation

  1. Étape 4.1 : Écrire un test de main(llm: LLMProvider, cases: list[GoldenCase]) -> int (code de retour) avec un FakeLLMProvider injecté et 1-2 GoldenCase synthétiques — vérifie que le code de retour est 1 si un WRONG_VALUE apparaît, 0 sinon. C'est la seule partie de la logique CLI testée en déterministe.
  2. Étape 4.2 : Implémenter cette main() injectable : pour chaque cas, extract_contract_facts(case.evidence, llm), puis score_case, accumule, imprime format_report(...), retourne has_wrong_value(...) en entier.
  3. Étape 4.3 : Ajouter le point d'entrée réel if __name__ == "__main__": qui construit le vrai OpenRouterProvider (même config que policybot/api/deps.py), échoue avec un message clair si OPENROUTER_API_KEY est absent, appelle discover_golden_cases(), puis main(llm, cases), et fait sys.exit(...) avec le code retourné.
  4. Fin de phase : pytest tests/contract/test_extraction_eval.py -v toujours vert (avec le Fake), et le script est exécutable manuellement.

Phase 5 — Run réel & revue

  1. Étape 5.1 : Lancer python -m policybot.contract.extraction_eval pour de vrai (clé OpenRouter déjà en .env).
  2. Étape 5.2 : Lire le rapport avec l'utilisateur : combien de MATCH/WRONG_VALUE/WRONG_ABSTAIN, et si un WRONG_VALUE révèle un vrai problème de prompt (pas juste une vérité terrain à corriger).
  3. Étape 5.3 : Si le run révèle une fixture expected.yaml mal renseignée plutôt qu'une vraie erreur d'extraction, corriger la fixture (pas le prompt) et relancer.

Risques & mitigations

RisqueMitigation
La vérité terrain (premier jet de Claude) contient une erreur de lecture de contrat Checkpoint 3.3 obligatoire avant de figer — l'utilisateur valide avant tout run compté
Non-déterminisme du vrai LLM : un même run peut varier Assumé et documenté — c'est un outil de suivi tendance, pas un gate CI ; jamais dans pytest -v
Coût des appels API à chaque run Script manuel, jamais automatique ; réutilise le modèle déjà configuré (pas de comparaison multi-modèles qui multiplierait les appels)
Le texte de CGU réel dérive avec le temps (fixture périmée) Date de capture en en-tête de evidence.txt ; dérive = signal pour rafraîchir, pas un bug du harnais

Critères de succès

  • pytest -v reste 100 % vert, offline et déterministe (aucune fixture golden réelle requise pour la suite standard)
  • python -m policybot.contract.extraction_eval tourne de bout en bout sur les 3 outils et produit un rapport lisible
  • Le code de sortie reflète correctement la présence d'au moins un WRONG_VALUE
  • Les 3 expected.yaml ont été relus et validés par l'utilisateur avant d'être considérés comme vérité terrain figée
