PolicyBot — du wizard au formulaire ingéré

Le formulaire sort du produit. PolicyBot devient une bibliothèque et une commande qui avalent un export Microsoft Forms et rendent 17 constats sourcés.

Date : 2026-08-10 Branche : main État de départ vérifié : 126 tests au vert

Le virage en une phrase

Aujourd'hui PolicyBot est un wizard web en 7 étapes qui, à la fin, lance des recherches. Demain PolicyBot n'a plus d'interface : tu envoies un formulaire Microsoft Forms aux demandeurs, tu télécharges l'export Excel des réponses, et une commande transforme chaque réponse en dossier de constats.

# aujourd'hui navigateur → wizard 7 étapes (HTMX, 1004 lignes) → 17 recherches Exa → rapport # demain Microsoft Forms → export .xlsx → policybot ingerer → 17 recherches Exa → rapport

Ce que ça change vraiment : le cœur du produit (les 17 recherches, l'ancrage des citations, le cache ARP, le rendu) ne bouge pas d'un octet. C'est tout ce qui l'entoure qui disparaît.

Phase 0 — Le filet de sécurité à faire en premier

Les questions du formulaire n'existent nulle part ailleurs que dans les gabarits Jinja du wizard. Si le wizard est supprimé avant d'être transcrit, le contenu du formulaire est perdu. Cette phase précède toute suppression.
  1. Étape 1 : transcrire les 35 questions du wizard dans configs/formulaire.yaml — intitulé exact, type, choix, champ du schéma alimenté, caractère obligatoire. Le catalogue complet est donné plus bas dans ce plan.
  2. Étape 2 : committer ce fichier seul, avant de toucher au reste. Il devient la source de vérité du formulaire.

Phase 1 — Le contrat d'entrée

Un module policybot/intake/ avec trois fichiers et une règle : le schéma et le catalogue de questions se valident mutuellement à l'import, exactement comme contract/criteres.py valide déjà la couverture des 17 critères. Une question qui ne pointe vers aucun champ, ou un champ obligatoire que le formulaire ne demande pas, fait planter l'import.

  1. Étape 1 : intake/schema.py — DemandeIAG (Pydantic). Reprend les 35 champs du WizardState, moins la mécanique de navigation. C'est ce que la CLI produit et ce que l'orchestrateur consomme.
  2. Étape 2 : intake/formulaire.py — charge configs/formulaire.yaml, le valide contre DemandeIAG, et expose le catalogue. Refuse un champ inconnu et un champ obligatoire non couvert.
  3. Étape 3 : une fonction devis() qui imprime le formulaire à recopier dans Microsoft Forms, avec pour chaque question le champ qu'elle alimente.
  4. Étape 4 : DemandeIAG.vers_entrees_orchestrateur() — produit le RequestInfo, la liste usage_inputs et le ContractOfferingIdentity attendus par Interview.assess(). Aucune signature existante n'est modifiée.
Perte de capacité assumée. Le wizard gérait plusieurs usages par demande (saved_usages). Microsoft Forms n'a pas de section répétable : une réponse = un usage. Pour deux usages, le demandeur remplit le formulaire deux fois. À écrire noir sur blanc dans le formulaire lui-même.

Phase 2 — Le lecteur d'export

  1. Étape 1 : intake/reponses.py — lit un .xlsx Forms (ligne 1 = intitulés des questions, une ligne par réponse) via openpyxl et rend une list[DemandeIAG].
  2. Étape 2 : l'appariement se fait sur l'intitulé normalisé (espaces réduits, casse et accents ignorés, ponctuation finale tolérée). Microsoft Forms ajoute ses propres colonnes — ID, Heure de début, Heure de fin, Adresse de courriel, Nom — qui sont ignorées sans bruit.
  3. Étape 3 : les choix multiples arrivent joints par ; et sont redécoupés vers list[str]. Les oui/non deviennent des booléens.
  4. Étape 4 : une colonne attendue et absente ne fait pas planter le lot : la demande concernée est rejetée avec son motif, les autres passent. Même principe que l'isolation d'une recherche Exa en échec.
  5. Étape 5 : un .xlsx de fixture committé sous tests/fixtures/, généré par le code de test lui-même pour rester lisible en diff.
Les intitulés de questions sont du texte de formulaire, pas des données de demandeur : ils peuvent apparaître en clair dans les messages d'erreur. Les réponses, elles, restent soumises à mask_text() dans les traces.

Ce qui manquera encore après ce lot

Inventaire honnête, classé par gravité. Rien de tout ceci n'est dans le périmètre — c'est ce qui reste sur la table.

ManqueGravitéCe que ça coûte
Aucune mesure de la qualité des recherches
Le harnais d'évaluation est mort avec le pivot vers Exa.		 critique Modifier un YAML de critère est un pari. Le document d'analyse mesurait 8 faits acceptés sur 19 ; aujourd'hui plus rien ne mesure. On ne peut ni prouver un progrès ni détecter une régression.
Le périmètre de l'offre n'est pas contrôlé
Aucun filtre n'écarte une page hors-offre avant extraction.		 critique Une garantie Enterprise peut être présentée comme applicable à une offre grand public — avec une citation ancrée, donc crédible. C'est le seul défaut du système qui produit une fausse conclusion plutôt qu'une absence de conclusion.
expires_at jamais renseigné ni respecté élevé Le cache ARP n'expire que par version de schéma. Une analyse d'août 2026 sera resservie intacte en 2028, alors que les conditions du fournisseur auront changé plusieurs fois.
Aucun test avec une vraie réponse Exa élevé Toute la suite passe par un faux client. Un changement de forme de la réponse Exa ne serait vu qu'en production.
Aucune intégration continue moyen Les tests ne tournent que sur ta machine, quand tu y penses.
Le gabarit DOCX dépend du dépôt

Aucun suivi du coût cumulé moyen Le plafond budgétaire est par exécution. Rien n'empêche cinquante exécutions à 0,90 $.
Rien ne relie les constats à une recommandation par conception La grille MCN a été supprimée et le README assume que l'officier décide. C'est cohérent, mais ce n'est écrit nulle part comme une décision de conception — seulement comme une absence.
Si un seul de ces points devait passer devant les autres : le harnais d'évaluation. Sans lui, les deux critiques suivants ne peuvent même pas être travaillés — il n'y a aucun moyen de savoir si une correction corrige quoi que ce soit.

Risques

Perdre les questions du wizard. Elles ne vivent que dans les gabarits Jinja. Parade : la Phase 0 les transcrit et les committe avant toute suppression, et l'ordre des phases est non négociable.
Les intitulés du formulaire dérivent. Renommer une question dans Microsoft Forms casse silencieusement l'appariement des colonnes. Parade : l'appariement se fait sur intitulé normalisé, une colonne attendue absente est signalée nommément, et --dry-run permet de le vérifier avant toute dépense.
Supprimer plus que du mort. Onze symboles ont été vérifiés sans appelant, mais la suite passe de 126 tests à moins — supprimer tests/web/ fait baisser le compte, ce qui masque une régression réelle. Parade : juger sur « zéro échec » et sur les nouveaux tests d'ingestion, jamais sur le total.
Le vrai export Forms ne ressemble pas à la fixture. La fixture est écrite par nous. Parade : faire un envoi réel du formulaire à soi-même, exporter, et passer ce fichier en --dry-run avant de déclarer la chaîne bonne. C'est la seule étape que le code ne peut pas vérifier tout seul.
