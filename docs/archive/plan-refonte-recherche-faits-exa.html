Refonte de la recherche des faits — passage à Exa

Une recherche web par fait, pilotée par une config YAML par recherche, avec structured output Exa et vérification par ancrage de la citation.

Date : 2026-07-21 Projet : PolicyBot (UQAM) Portée : couche contract/ — collecte & extraction des faits ARP Type : plan d'architecture

1 — Objectif

Remplacer entièrement le pipeline Tavily actuel (une recherche + une extraction LLM par famille de 5 familles) par un pipeline Exa où chaque fait contractuel a sa propre recherche web, décrite par un fichier YAML dédié.

Le structured output d'Exa (schéma JSON passé dans contents.summary) renvoie directement, pour chaque fait, une valeur et une citation verbatim. PolicyBot vérifie ensuite cette citation en l'ancrant dans le texte réellement récupéré de la source : une citation non ancrée fait retomber le fait à unknown. Le but de la refonte est la vérifiabilité fait par fait.

Validé côté API Exa — /search accepte contents.summary.schema (JSON Schema → structured output) et renvoie par résultat : url, title, text, highlights (extraits verbatim + scores) et summary. On tient donc à la fois la valeur structurée et la matière verbatim pour l'ancrer.

4 — Anatomie d'une config de fait une recherche = un YAML

Chaque fichier décrit intégralement une recherche Exa : la requête, les domaines à cibler, et le schéma structured output qui impose la forme {value, quote}. Exemple pour training_default :

# configs/recherche_des_faits/training_default.yaml version: 1 fact: training_default category_arp: "Souveraineté et hébergement des données" # informatif allowed_values: ["yes", "no", "unknown"] hint: >- yes si le contenu soumis sert à l'entraînement par défaut ; no seulement si l'offre évaluée le désactive par défaut. exa: query: "{tool} {vendor} terms: is customer content used to train models by default" type: auto # neural | keyword | auto num_results: 5 include_domains: [] # injecté depuis le registre outil si dispo contents: text: { max_characters: 8000 } highlights: query: "training on customer data / opt out" num_sentences: 3 summary: query: "Does the assessed offering use submitted data to train models by default?" schema: # ← STRUCTURED OUTPUT — forme appréciée par Exa description: "Preuve d'un fait contractuel PolicyBot" type: object additionalProperties: false required: [value, quote, source_url] properties: value: { type: string, enum: ["yes", "no", "unknown"], description: "La valeur du fait, strictement dans la liste permise" } quote: { type: string, description: "Phrase verbatim de la page prouvant la valeur" } source_url: { type: string, description: "URL exacte de la page d'où provient la citation" }
Ancrage (le cœur de la vérif). Exa renvoie value + quote. On accepte le fait seulement si quote se retrouve, à la mise en forme près, dans le text ou les highlights réellement récupérés pour ce résultat — la fonction _quote_is_anchored existante est réutilisée telle quelle. Sinon → unknown / outcome=citation_rejected. C'est ce qui distingue « Exa l'a dit » de « c'est écrit dans la source, à cette URL ».

5 — Exécution, parallélisme & cache

  1. Cache d'abord — PreApprovedStore renvoie l'ArpRecord si présent et non périmé. Aucune recherche Exa n'est lancée.
  2. À froid : 24 recherches concurrentes — un ThreadPoolExecutor borné (ex. 8 workers) lance les recherches par fait. Latence perçue ≈ une seule recherche.
  3. Dégradation par fait — une recherche Exa qui échoue (réseau/quota) marque ce fait unknown (outcome=collection_failure) sans jamais interrompre l'entrevue. Distinction auth / quota / network conservée pour la traçabilité.
  4. Assemblage — les 24 FactEvidence forment ContractFacts ; build_arp en dérive les 13 critères ; l'ArpRecord est mis en cache.
Garde-fou de traçabilité (non négociable). tracing.py ne journalise jamais de texte libre en clair. Les requêtes, citations et contenus de page restent masqués (mask_text — longueur + hash SHA-256 tronqué). Tout nouveau point de trace dans exa.py doit respecter cette règle. L'artefact d'audit Markdown (équivalent de la sortie output/tavily/) devient output/exa/ et n'est pas une trace.

7 — Risques & mitigations

#RisqueMitigation
R1 Le structured output d'Exa est produit par un LLM interne — la value et la quote peuvent être hallucinées. Ancrage déterministe obligatoire : quote non retrouvée dans text/highlights → unknown. C'est exactement le principe « rien de dérivé n'est silencieusement digne de confiance ».
R2 Faux négatifs d'ancrage — Exa peut reformuler la citation (paraphrase, ponctuation) et casser le in textuel. Ancrer aussi contre highlights (extraits verbatim par construction), garder la normalisation existante (markdown/guillemets/espaces), seuil minimal de longueur. Régler num_sentences des highlights pour couvrir la phrase-preuve.
R3 Coût & rate-limit — 24 recherches × contents(text+summary schema) par outil, en parallèle. Cache SQLite (la majorité des cas), pool borné (ex. 8 workers), num_results bas, include_domains ciblés par fait, max_characters plafonné. Surveiller la facturation Exa lors du 1er passage réel.
R4 Invariant architectural — le summary d'Exa est une extraction « type LLM ». Risque de brouiller la règle « le LLM ne décide jamais du verdict ». Documenter explicitement : la valeur Exa reste une proposition vérifiée (origin=llm_proposed/ancrée), jamais un verdict. Seuls la matrice MCN et grille.yaml décident. Mettre à jour le tableau d'invariants de CLAUDE.md.
R5 Régression du scénario doré — le e2e UQAM (ChatGPT + Protégé B → INTERDIT/Refuser) ne doit pas bouger. Le verdict vient de la matrice, pas des faits Exa : garder tests/test_golden_scenarios.py vert avec un FakeExaClient scénarisé. C'est le filet de sécurité de la migration.
R6 Empaquetage — le nouveau dossier configs/recherche_des_faits/ doit être livré dans le wheel. Le déclarer comme package data dans pyproject.toml (dette d'empaquetage déjà connue à corriger au passage).

8 — Départage multi-sources piste à trancher

Le problème. Pour un fait, Exa /search renvoie N résultats (ex. 5), et le summary.schema s'applique par résultat — soit jusqu'à N candidats {value, quote, source_url}. Après ancrage, il peut en rester plusieurs, éventuellement avec des valeurs contradictoires. Il faut en retenir un.

Note : comme le summary est par résultat, la source d'un candidat est intrinsèquement connue (l'URL du résultat). Le champ source_url du schéma est ce que le LLM d'Exa déclare ; il sert de garde-fou (piste D), pas de source de vérité.

PisteMécaniqueBilan
A — Rang par type de source
recommandée
0 LLM		 Chaque candidat est ancré contre le texte de son résultat. Parmi les candidats ancrés, tri par source_policy (contractuel > DPA > technique officielle > commercial > secondaire), puis par score de pertinence Exa. Le 1er gagne. ➕ Déterministe, respecte la décision « LLM supprimé », auditable.
➖ Ne raisonne pas sur une contradiction de fond entre deux sources également fiables.
B — Consensus + drapeau de conflit
recommandée
0 LLM		 Comme A, mais si des candidats ancrés portent des valeurs différentes, on retient la source la plus autoritaire et on pose needs_officer_confirmation sur le fait (avec les deux citations conservées pour l'officier). ➕ Conservateur « quand on hésite, on signale », fidèle aux principes PolicyBot.
➖ Un peu plus de logique + un champ de conflit à faire remonter au rapport.
C — Arbitre LLM
ton idée
réintroduit 1 LLM		 On rassemble les candidats déjà ancrés (quote + url) et on demande à un petit LLM de désigner l'URL qui répond le mieux, en la choisissant dans la liste fournie. Sa réponse (une URL) est re-validée contre la liste ; il n'invente ni valeur ni citation. ➕ Gère finement les cas ambigus, garde le LLM « cantonné » (il choisit, il n'extrait pas).
➖ Tension avec la décision verrouillée « Exa extrait, LLM supprimé » ; latence/coût par fait contesté. À n'activer que sur conflit (rare) pour borner le coût.
D — source_url comme garde-fou
complément gratuit		 Puisque le schéma fait déclarer source_url au LLM d'Exa, on exige qu'il coïncide avec l'URL du résultat traité. Une divergence est un signal d'hallucination → on écarte le candidat. ➕ Anti-hallucination gratuit, se combine avec A/B/C.
➖ Ce n'est pas un départage à lui seul.
Recommandation. Partir sur A + B + D (entièrement déterministe, conforme aux décisions verrouillées, aucun LLM). Garder C en option activable uniquement sur conflit si, à l'usage, A/B se révèlent trop grossiers. Ton intuition « faire dire au LLM d'où vient la citation » est donc doublement présente : en garde-fou passif (piste D, sans appel LLM supplémentaire) et en arbitre actif optionnel (piste C).

9 — Questions ouvertes

  • Q1 — include_domains par fait. Injecte-t-on automatiquement les domaines de contract_sources du registre outil dans chaque config de fait, ou laisse-t-on la recherche ouverte ? Proposition : injecter si connu, sinon ouvert.
  • Q2 — extraction_confidence global. Le champ confidence par fait est retiré du schéma Exa. Proposition : recalculer extraction_confidence comme la proportion de faits portant une citation ancrée (part d'accepted) — un signal de couverture, pas une probabilité.
  • Q3 — Parallélisme réel. ThreadPoolExecutor suffit (I/O réseau) — confirmer le nombre de workers et le comportement sous rate-limit Exa (backoff ?).
  • Q4 — Activation de l'arbitre (piste C). Le laisse-t-on désactivé par défaut, activable par flag, ou l'écarte-t-on complètement pour préserver strictement « 0 LLM » ?
